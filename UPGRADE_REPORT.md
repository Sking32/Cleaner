## Проверить вручную

Сначала используйте отдельную Windows VM со снимком. Не начинайте с глубокого пресета на рабочем компьютере.

1. Интерфейс: русский/английский язык, масштаб 100–200%, кнопки запуска/остановки служб, выбор диска и сообщение с теневыми копиями.
2. Безопасная файловая проба: небольшой тестовый каталог → просмотр → карантин → восстановление → повторный перенос. Проверьте исключённую вложенную папку и отсутствие ложного сообщения об освобождённом месте.
3. Твик с несколькими значениями: зафиксируйте исходные значения, примените и отключите; убедитесь, что вернулись все значения и их типы.
4. Точка восстановления: защита включена, выключена, нет прав администратора, ограничение частоты Windows. При неудаче опасная операция должна остановиться.
5. Только на VM: исходные режимы служб running/stopped и AutomaticDelayed, ошибки доступа, отмена, восстановление после неудачи.
6. Только на VM: powercfg, netsh, wevtutil, DISM, ScheduledDefrag и VSS. Для VSS проверьте 0, 1 и несколько копий; последняя должна сохраниться. Наличие поддержки конкретных твиков зависит от сборки Windows и оборудования.
7. История и страницы состояния: переходы после применения/отката; внешнее изменение настройки; предупреждение о расхождении; отметки необходимости перезагрузки после включения и отключения.
8. Старые бэкапы: сохраните копию %LOCALAPPDATA%\Cleaner перед первым использованием обновлённой версии. Неполные старые данные требуют ручного восстановления из собственных резервных копий или точки восстановления.

## Оставшиеся ограничения

Недостающие исходные значения из старых бэкапов восстановить автоматически невозможно. Повреждённые записи карантина сохраняются для ручного разбора; UI не является инструментом ремонта таких записей. Карантин на другом томе может не принять каталог: данные должны остаться на исходном месте, а операция сообщит об ошибке.

Обычная отмена не возвращает уже обработанные файлы автоматически. Некоторые системные операции необратимы: корзина, Windows.old и удаление старых теневых копий. Точка восстановления не заменяет резервную копию личных файлов.

Аппаратная применимость твиков, реальные Windows API и визуальное поведение WPF требуют ручной проверки. Автоматические проверки не доказывают, что каждый твик полезен на конкретном компьютере. Современные версии Windows могут игнорировать устаревшие политики.

Дальнейшие улучшения: таблица совместимости твиков по сборкам Windows и оборудованию, проверка интерфейса в Windows VM, оценка скорости карантина на больших кэшах и переход к пакетному журналу с сохранением гарантий восстановления.

Технические справочники, сверенные при исправлении команд: [reserved storage](https://learn.microsoft.com/en-us/powershell/module/dism/get-windowsreservedstoragestate?view=windowsserver2025-ps), [Remove-CimInstance](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/remove-ciminstance).

## Дополнение: удаление старого карантина — 13.10.2026

Причина ошибки на файле `00001_ClrBindingWorker.cs` подтверждена чтением его атрибутов: `ReadOnly, Archive`. Перенос в карантин сохраняет атрибут «только чтение», а прежний вызов `File.Delete` его не учитывал.

- При безвозвратном удалении снимается только атрибут «только чтение» у удаляемых файлов и каталогов. Права доступа и владельцы не изменяются. Восстановление сохраняет исходный атрибут.
- Вложенные каталоги удаляются снизу вверх с проверками ссылок. Старый формат журнала остаётся совместимым; исправление действует и для очистки старых сессий.
- Заблокированные и недоступные записи остаются в журнале для повторной попытки. Другие записи могут удалиться; интерфейс показывает количество завершённых удалений, оставшихся записей и первую ошибку.
- Перед удалением проверяется возможность сохранения журнала. Несоответствие фактического типа записи журналу блокирует удаление этой записи.

Сборка решения прошла без ошибок и предупреждений. После отдельного разрешения выполнены 62 связанные изолированные проверки: карантин, восстановление, регрессии и локализация. Все прошли, включая 8 новых сценариев удаления. Реальный карантин при исправлении не изменялся; у проблемного файла только прочитаны атрибуты и права доступа.

Ручная проверка: остановить прежний сеанс отладки, запустить обновлённую сборку и проверить удаление сессии через интерфейс. Удаление остаётся безвозвратным. Если другой файл занят или его ACL запрещает удаление, приложение должно сохранить запись и показать ошибку; принудительная смена прав не выполняется.

## Большой этап улучшений — 13.10.2026

### Карантин и восстановление

- Добавлена проверка целостности без изменения данных: повреждённый или отсутствующий журнал, незарегистрированные файлы, незавершённые операции, отсутствующие записи и ссылки на каталоги.
- Проблемные сессии видны в интерфейсе. Разрешённые действия зависят от состояния: повреждённые данные нельзя автоматически удалять, валидные записи можно восстанавливать.
- Конструктор больше не создаёт пустой журнал поверх сессии с незарегистрированными файлами и отвергает JSON null. Журнал и предки проверяются на ссылки.
- Удаление, восстановление и очистка старых сессий поддерживают отмену и прогресс по записям. Уже завершённые действия сохраняются; оставшийся журнал позволяет повторить операцию.
- Проверка дерева при восстановлении и удаление вложенных файлов реагируют на отмену. Очистка старых сессий показывает число успешных и неудачных сессий, а не скрывает ошибки.

### Диагностика и история

- Экспорт локального JSON-отчёта о последнем просмотре/очистке и операциях карантина. Для CLI добавлен --report.
- Отчёт содержит версию формата, окружение, просмотр/выполнение, результаты, ошибки и отменённые операции. Для PathCleanup записываются причины пропусков: защита, исключение, отказ карантина. Детали ограничены 250 записями; указано число остальных.
- История сохраняет неудачные и отменённые запуски с результатами операций. JSON null в настройках больше не заменяется новым пустым документом.
- Переданный runner токен отмены связывается с токеном контекста и достигает обработчиков. Результат завершённых операций сохраняется при отмене следующей.
- Отчёты не отправляются автоматически. Ошибки и пути могут содержать личную информацию; её нужно проверить перед передачей.

### Совместимость

- Добавлены ограничения minWindowsBuild/maxWindowsBuild и список verifiedWindowsBuilds с валидацией.
- Проверка выполняется в ядре до применения. В интерфейсе неподдерживаемый твик нельзя включить, но ранее применённый можно отключить.
- Для девяти твиков категории Windows 11 задан минимальный build 22000. Указание этой границы опирается на [данные Microsoft о Windows 11 21H2](https://learn.microsoft.com/en-us/windows-insider/older-windows-insider-preview-builds). Это ограничение целевой платформы; эффект конкретных политик на разных редакциях и оборудовании пока не подтверждён.
- Подтверждённые сборки не выдумываются: список пока пуст. Таблица всего каталога находится в COMPATIBILITY.md.

### Проверки и инцидент изоляции

Во время первого запуска новый тест отмены ошибочно использовал операцию temp_user с настоящим пользовательским Temp. Запуск был остановлен после обнаружения ошибки. В тестовый карантин успели переместиться 176 файлов. Ни одна из этих 176 записей не была потеряна: перед восстановлением проверены наличие всех сохранённых файлов и отсутствие совпадений имён.

После явного разрешения владельца все 176 файлов восстановлены через журнал без перезаписи; результат — Restored=176, Failed=0. Дополнительно подтверждено наличие всех 176 исходных путей. В прерванном тестовом каталоге остались только пустой журнал и временная копия журнала. Копия исходного журнала и результат восстановления сохранены локально в .recovery, которая исключена из Git из-за личных путей.

Ошибочный тест переписан на управляемую заглушку без файловых путей. Добавлен run-isolated-tests.ps1: TEMP/TMP направляются в .test-sandbox внутри проекта. Обе тестовые сборки до запуска сценариев проверяют корень Temp и отсутствие ссылок; прямой запуск также получает отдельный Temp в каталоге сборки. Категория WindowsIntegration исключена настройками и фильтром скрипта. Эта дополнительная защита не заменяет проверку системных команд и путей в каждом тесте.

Повторный запуск: 369 изолированных тестов успешно, 338 Core и 31 CLI. Реальные команды Windows, службы, твики и нативные тесты реестра на этом этапе не запускались. Последняя сборка решения прошла без ошибок и предупреждений.

Один из промежуточных повторов не подтвердил удаление пустой сессии в RestoreAll_Removes_Session_Directory_When_Complete. Добавлена диагностика результата восстановления и оставшихся файлов. Следующие четыре полных запуска прошли подряд (369/369 каждый); причина единичного сбоя не установлена, поэтому он не объявляется исправленным. При повторении нужно сохранить сообщение ошибки и проверить блокировки файлов в VM.

### Что проверить вручную перед выпуском

1. WPF: русский/английский, масштаб 100–200%, длинные ошибки, доступность новых кнопок. Экспорт JSON после просмотра, успешной операции, частичного сбоя и отмены.
2. Только собственные пробные файлы: перенос → восстановление → повторный перенос → отмена удаления. Убедиться, что остаток виден и доступна повторная попытка. Безвозвратное удаление выполняется только для этих пробных файлов.
3. Созданные специально для проверки копии сессий: повреждённый/отсутствующий журнал, лишний файл, незавершённый перенос. Проверка целостности не должна изменять файлы.
4. Windows VM со снимком: неподдерживаемые версии, права администратора, заблокированные файлы, реальные службы и команды, восстановление после ошибки/перезапуска. Заглушки не подтверждают эти сценарии.
5. Процесс приложения: повторный запуск после замены сборки. Ошибка отладчика старого сеанса не подтверждает работу новой сборки.

Концепцию редизайна можно начинать сейчас. Полный перенос интерфейса — после короткой ручной проверки новых сценариев WPF; перед выпуском требуется VM-проверка реальных изменений. Подробнее: REDESIGN_READINESS.md.
